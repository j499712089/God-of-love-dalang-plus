## A. 用户展示面建档（使用者自己的档案）

**目的**：建立使用者自己的展示面档案，后续匹配度分析、话术设计必须引用档案中的具体优势，禁止泛泛而谈。

### A0. 隐私边界（最高优先级，违反即错）

**技能知识库内禁止存放任何用户的个人身份信息**（真实姓名、职业、年龄、城市、收入、恋爱经历、前任细节、设备/技能栈、平台账号等）。知识库只允许存放通用的方法论规则与话术模板。

**首次调用强制询问**：无论本机记忆、历史会话、系统档案里是否已有用户信息，**用户未主动提供本技能资料时，一律视为未知**。禁止从系统记忆/历史会话/用户画像推断用户身份、职业、年龄、收入、所在地；禁止用推断结果做匹配度分析或话术设计。必须主动询问：

> "请提供你的社交平台展示面资料（截图或口述：年龄/职业/年薪/城市/展示面文案/照片风格/恋爱目标），我先建你的档案再分析。"

**用户未提供资料前的输出限制**：
- 可以输出：对方画像分析、真实性核验、通用聊天原则
- 禁止输出：匹配度分析（必须引用用户档案，禁止用推断身份代替）、引用用户职业/身份定制话术、任何"你档案里X优势"表述

**匹配度分析红线**：只能引用用户本次明确提供并写入 `profiles/` 的档案内容。档案中标注「未提供」的字段，匹配度分析中不得出现。

### A1. 询问社交平台

先问用户："你在哪个平台使用本技能？"

- 探探 / 积目 / SOUL / 牵手 / 陌陌 → 交友平台档案
- 抖音 / 微博 / 小红书 → 内容平台档案
- 微信 → 私域档案

### A2. 收集用户资料（截图或口述任选）

告知用户："请提供你的社交平台展示面资料，可以**直接发截图图片**，也可以**口述**（年龄/职业/年薪/城市/展示面文案/照片风格/恋爱目标等）。"

口述时必须逐项采集（缺项明确标注"未提供"）：

1. 基础信息：年龄、身高、星座、学历、职业、年薪、家乡、现居地
2. 展示面文案："关于我"、"想找个人一起"
3. 照片情况：数量、场景分布（旅行/运动/工作/生活）、风格（精修/原图/氛围感）
4. 恋爱性格：自称类型、约会偏好
5. 标签：资料页挂的标签
6. 恋爱目标：结婚/认真恋爱/随缘
7. 核心优势：最拿得出手的 1-3 点

**图片资料**：逐张读取截图内容，按上述字段提取，缺失字段询问用户补全。

### A3. 建立用户档案

按模板创建 `profiles/用户档案_<平台>.md`（模板见 `references/用户档案模板.md`）。

- 示例：`profiles/用户档案_探探.md`、`profiles/用户档案_抖音.md`
- 多平台可建多份，**平台之间严格隔离，禁止混用**
- 标注「建档日期」和「数据来源（截图/口述）」，禁止编造用户未提供的信息

### A4. 确认需求（必须问清楚）

1. **"你要分析的对象资料来自哪个平台？"**（与用户自己的平台可不同）
2. **"你想了解哪些信息？"**（多选：对方真实情况 / 资料真实性核验 / 恋爱观 / 是否值得继续 / 聊天建议）
3. **"接下来你想怎么做？"**（已匹配没聊 / 聊天中 / 已转微信 / 想约见面）

用户的回答决定本次分析的侧重点。**未确认需求前不输出完整分析。**

## B. 女生资料卡（每个女生一张 JSON 卡）

**收到女生资料（截图/简介/口述）后，如用户未表态是否建档，先问一句再动。**

> 「库里还没有这个女生的资料卡。要新建吗？
> · **新建**（推荐）→ 我生成资料卡写进档案库，后续每次聊天都能增量更新、算兴趣度、进排行榜
> · **只看一次** → 我只在对话里分析，不落库，下次再问我就没有记忆了」

| 用户答复 | 动作 |
|---------|------|
| 新建 / 嗯 / 好 | `new` 建卡 → 分析 → 回填 → `validate` → 验收 |
| 只看一次 / 不用 | 只做对话内分析，**禁止**写任何文件；结尾提醒「本次未落库」 |
| 未回答 | 停在询问，不得擅自建档，也不得擅自跳过分析 |

**唯一例外**：用户明确说「更新 XX 的档案」「继续上次那个」——已表达建档意图，直接查重后更新，不必再问。

> ⚠️ 区分清楚：A 节建的是**用户自己**的展示面档案（markdown，一次性）；本节建的是**每个女生**的资料卡（JSON，可持续更新）。两者互不替代。

### B1. 库位置

**档案库不在技能包内，而在用户自己的目录**（技能升级/重装会覆盖技能包，档案放包内会被冲掉）。

#### 🔴 目标库判定硬门（2026-09-15 事故根因修正，优先级高于本节其余全部内容）

**本机（主人自用机）已存在真实档案主库，它是唯一权威目标：**

```
D:\01-AI任务中心\CODEBUDDY\任务工作空间\女生档案库
```

**判定顺序（建档前按顺序查，命中即停）：**

1. `…\CODEBUDDY\任务工作空间\女生档案库\data\profiles\` 存在**且非空** → **一律写入该库**。不再读 `~/.dalang/config.json` 的 `library_root`，也不再问库位置。
2. 上一条不成立 → 才走 `library_root`。
3. 两者都没有 → 才问用户；`D:\我的档案库` 只作为**全新机器首次建库**的默认落点。

**事故记录（禁止重犯）**：2026-09-15 给「冉红霞」建档时，Agent 只读到 `~/.dalang/config.json` 的 `library_root = D:\我的档案库` 就落库，把真实资料卡写进了只有测试卡的空库；主人 19 份真实档案全在 CODEBUDDY 库，造成档案分裂、看板里找不到人。

**硬规则：**
- **`library_root` ≠ 主人的真实档案库**。它只是 PLUS 首次建库的默认落点；本机存在 CODEBUDDY 主库时它作废。
- 禁止把 CODEBUDDY 库的真实资料卡复制进 `D:\我的档案库` 或技能包（隐私泄露），也禁止反向把模板卡写进主库（污染排名）。
- **跨客户端写入已获授权**：CODEBUDDY 库位于主人的 CODEBUDDY 客户端空间，主人已明确指令「统一到该库」。其它客户端（WorkBuddy 等）写该库视为已授权，但**只允许**动 `data/profiles/`、`data/_backup/`、`assets/`、`index.html` 与 `scripts/` 下的既有脚本；CODEBUDDY 空间内其它任何目录一律禁止碰。
- **建档前后各 `ls` 一次目标库 `data/profiles/` 并回报文件数**，作为「写对库了」的证据。

判定逻辑（**仅当上表第 1 条不成立时才用**）：
- 已有 `library_root` → **不再问**，直接用。
- 没有 → 才问一次：
  > 「还没配置档案库位置。你想把档案库存在哪？比如 `D:\我的档案库`、`E:\恋爱档案`，或直接说「D 盘」我就建 `D:\我的档案库`。」

拿到路径后执行一次：

```bash
node "<SKILL_ROOT>/scripts/cloud_client.js" set-lib "<用户给的路径>"
# 或（同时复制页面骨架并重建空排名）
cd "<SKILL_ROOT>/profile_db" && python scripts/profile_cli.py init --path "<用户给的路径>"
```

**init 输出给用户的关键行**（必须原样呈现）：`档案库已创建: <绝对路径>`、`示例卡: <路径>`、`网页入口: <绝对路径>`。

**硬规则**：
- 规约默认库根：Windows `D:\我的档案库`；macOS / Linux `~/.nvsheng/library`
- **🔴 禁止自创库路径**：只用「config.json 的 library_root / 用户明确指定 / 默认 `D:\我的档案库`」三处之一，禁止发明 `~/.dalang/library` 之类
- 迁移位置：先复制 `data/` 到新目录，再 `init --path <新路径> --force`
- 库根解析优先级：`--lib` CLI 参数 > 环境变量 `DALANG_LIB` > 统一配置 `~/.dalang/config.json` > 库根/PKG 指针 > 默认推荐位置

| 用途 | 路径 |
|------|------|
| **统一配置（key + 库根，每次调用必读）** | `~/.dalang/config.json` |
| 位置指针（库根自动生成） | `<库根>/library.json` + `<库根>/library-info.json` |
| 后端 CRUD 入口（首选） | `${SKILL_ROOT}/profile_db/scripts/profile_cli.py` |
| 单人资料卡 | `<库根>/data/profiles/<id>.json` |
| 字段规范（写前必读） | `<库根>/SCHEMA.md` |
| 前端入口（排行榜看板） | `<库根>/index.html` |
| 自动生成产物（禁止手改） | `<库根>/data/db.js`、`index.json`、`_backup/` |
| **安全硬门** | 找不到有效 `library_root` 时 `build_db.py` 直接 FAIL，**绝不回退写入技能包** |

查当前库根与网页绝对路径：`python scripts/profile_cli.py where`

### B2. 建档后必须追问的四个变量

若以下四项未知，必须放进 `gaps` 并在回复末尾直接问用户（不得跳过）：

1. **用户在哪个城市？**（异地是否硬推见面需用户拍板；**本机已知：主人遂宁人、在成都已 10 年，无需再问**）
2. **用户本次婚恋目标？**（认真找结婚对象 / 随缘看看 / 排遣孤单）
3. **用户对她资料的第一眼兴趣度（1-10）？**
4. **是否已发过消息？发了什么原话+时间戳？**

> 档案缺这些变量，后续匹配度与见面策略都会失真。

### B3. 标准建档命令串（照抄执行，禁止自创路径）

**静态看板唯一规约**：本技能不启动后端、不使用 API、不依赖端口、不做浏览器目录授权。首次选定库位置后，`init` 只创建用户库目录、复制静态页面骨架、写 `config.json` 并重建数据。看板唯一入口是 `<库根>/index.html`，数据源是同库 `<库根>/data/db.js`；不得把技能包内 `profile_db/data/` 当用户数据目录。Agent 每次新增/更新/删除资料卡，必须通过 `profile_cli.py` 写入 `<库根>/data/profiles/<id>.json`，随后 `rebuild`，最后 `validate` 与 `where`，并把 `where` 输出的 `<库根>/index.html` 绝对路径原样发给用户。页面编辑失焦自动保存只写该浏览器 `localStorage` 覆盖层，不代表已改写 JSON 源文件。`profile_server.py`、`127.0.0.1`、`39123` 均为废弃兼容代码，不得作为建档或发看板流程。

```bash
cd "<SKILL_ROOT>/profile_db"

# ① 首次建库（仅当 config.json 无 library_root）
python scripts/profile_cli.py init --path "D:\我的档案库"

# ② 新建档案卡（查重后：库里没有才 new）
python scripts/profile_cli.py new --id <拼音_平台> --name <昵称> --platform <平台>

# ③ 填事实 → 时间线 → 打分 → 结论
python scripts/profile_cli.py set --id <id> --field facts.年龄 --value 27
python scripts/profile_cli.py timeline-add --id <id> --t 第1轮 --who 她 --text "原话" --gap 8h
python scripts/profile_cli.py score --id <id> --intent 20 --speed 15 --respond 12 --match 10 --truth 7 --risk 8
python scripts/profile_cli.py verdict --id <id> --value 推进中

# ④ 验收 + 拿网页路径
python scripts/profile_cli.py validate --id <id>
python scripts/profile_cli.py where
```

**七条防呆硬规则（违反 = 未完成）：**

1. **禁止自创库路径**：先用 B1「目标库判定硬门」定库——**本机恒为 `D:\01-AI任务中心\CODEBUDDY\任务工作空间\女生档案库`**；仅在该库不存在时才用三处之一（config.json / 用户明确指定 / 默认 `D:\我的档案库`）。
2. **禁止越界写入**：业务源文件只允许写 `<库根>/data/profiles/<id>.json`；禁止写技能包、工作区记忆、桌面、下载或未授权路径。
3. **禁止手动改自动产物**：`data/db.js`、`data/index.json` 只能由 `rebuild` 生成。
4. **禁止伪成功**：写入后必须检查目标文件存在、JSON 可解析、`id` 与文件名一致、`library_root` 未漂移；任一失败立即停止。
5. **重建位置自检**：每次操作后必须 `rebuild` + `where`；库根不是用户库立即停止修正。
6. **每一步必须有证据**：记录 `init/new/set/patch/timeline/score/verdict/rebuild/validate/where` 的实际执行结果。
7. **页面编辑边界**：`localStorage` 不等于已写入 JSON；正式写源文件必须走 CLI，并重新 `rebuild + validate`。

### B4. 资料卡增删改查（统一走 CLI，禁止手写 JSON）

CLI 内建查重、枚举校验、分数上限、模板字段白名单、删除前自动备份，写入后自动重建排名。手写 JSON 会绕过全部校验。

| 操作 | 命令 |
|------|------|
| 查（全库排名） | `python scripts/profile_cli.py list` |
| 查（单卡/单字段） | `python scripts/profile_cli.py get --id <id> [--field plan.rounds]` |
| 增（建卡，自动查重） | `python scripts/profile_cli.py new --id <id> --name <名> --platform <平台>` |
| 改（单字段） | `python scripts/profile_cli.py set --id <id> --field facts.职业标签 --value "老师"` |
| 改（批量合并） | `python scripts/profile_cli.py patch --id <id> --file patch.json` |
| 改（兴趣度分项） | `python scripts/profile_cli.py score --id <id> --intent 25 --speed 20` |
| 改（结论） | `python scripts/profile_cli.py verdict --id <id> --value 推进中` |
| 追加互动时间线 | `python scripts/profile_cli.py timeline-add --id <id> --t 第3轮 --who 她 --text "在忙" --gap 8h` |
| 删（先自动备份） | `python scripts/profile_cli.py delete --id <id> --force` |
| 校验颗粒度 | `python scripts/profile_cli.py validate [--id <id>]` |
| 仅重建排名 | `python scripts/profile_cli.py rebuild` |

**大批量填充**：把 `facts`/`photos`/`truth_check`/`inferences`/`position`/`plan` 写成一个 JSON 文件，用 `patch` 一次合并，比逐条 `set` 省事。

### B5. 文件格式限定（硬约束）

| 项 | 限定 |
|----|------|
| 编码 | UTF-8 无 BOM，`\n` 换行 |
| 文件名 | `<id>.json`，`id` = `拼音_平台` 全小写下划线（正则 `^[a-z][a-z0-9_]*_[a-z]+$`），如 `xiaoyu_tantan` |
| 一人一文件 | 禁止一个文件塞多人，禁止同人多卡 |
| 顶层字段 | 严格等于模板 19 个键，**禁止新增顶层字段**；`facts` 内部可自由加键 |
| 枚举 | `verdict` ∈ {推进中, 观察中, 已止损}；`truth_level` ∈ {高, 中-高, 中, 中-低, 低} |
| 时间戳 | `created`/`updated` 为毫秒整数，由 CLI 自动维护 |
| 禁止手改 | `interest`（由分项自动加总）、`data/db.js`、`data/index.json` |

**固定模板 19 字段**：`id`、`name`、`platform`、`verdict`、`interest`、`interest_breakdown`、`truth_level`、`created`、`updated`、`facts`、`photos`、`truth_check`、`truth_note`、`inferences`、`position`、`plan`、`gaps`、`timeline`、`summary`。字段内部结构见 `profile_db/SCHEMA.md`。

### B6. 兴趣度六项分解（总分禁止手填）

| 键 | 含义 | 满分 |
|----|------|------|
| `intent` | 婚恋意愿强度 | 25 |
| `speed` | 推进/见面意愿速度 | 20 |
| `respond` | 响应质量（间隔+延展+反问）| 20 |
| `match` | 与用户展示面的契合 | 15 |
| `truth` | 真实性核验得分 | 10 |
| `risk` | 风险余量（越安全越高）| 10 |

**硬规则**：
- 无聊天记录（`timeline` 为空）时 `respond` 必须为 `0`，不得凭资料想象打分
- `verdict` 为 `已止损` 时脚本自动把总分锁在 30 以内
- `match` 必须引用用户档案中的具体优势；用户未建档则该项记 0 并写入 `gaps`

### B7. 颗粒度红线（低于此标准视为未完成）

`facts`（≥8 条键值）、`photos`（每张要 content + decode）、`truth_check`（五维，每维带 result + level）、`truth_note`、`inferences`（≥3 条，每条四件套：title / confidence / evidence / readings 至少两种解释 / means）、`position.chance` + `position.risk`、`plan`（stage / opener / opener_why / rounds / invite_rules / stop_rules / funnel_note）、`gaps`、`timeline`、`summary`。

**推断置信度纪律**：证据少于 2 项时 `confidence` 只能写 `信息不足`，且必须进 `gaps` 向用户索要。`validate` 会逐项拦截。

### B8. 互动时间线：后续每次聊天的落库入口

`timeline` 是**建档后的增量通道**。用户之后每次发来聊天截图、粘贴记录或口述进展，都逐条追加，不要重写整卡。

**触发场景**：用户说「她回了…」「今天聊了这些」「她说 XX」「隔了一天才回」——一律先追加时间线，再重算分数。

| 字段 | 内容 | 规范 |
|------|------|------|
| `t` | 轮次或时间点 | `第3轮` / `8月28日` / `转微信后` |
| `who` | 谁说的 | 默认 `用户` / `她`；**以目标库既有惯例为准**——本机 CODEBUDDY 主库统一用 `主人` / `她`，新卡必须跟随，禁止同一库内混用 |
| `text` | **原话原样** | 保留表情 `[破涕为笑]`、分段两空格、错别字，不得润色 |
| `gap` | 与上一条的真实间隔 | `47min` / `8h` / `25h`；确实不知道写 `未知` |
